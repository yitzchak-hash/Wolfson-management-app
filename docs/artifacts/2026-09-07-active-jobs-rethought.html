How to read a row

The name and its stage colour, the group it sits in, then the last touch: who, what, when. On the right, one small square per kind of touch inside the window, and how many touches there were — a job that was touched nine times this week is busier than one opened once, and the eye should see that without reading.

Three ways to rank it

★ A · Last touch first, with heat

The newest touch decides the order — the job somebody just used is on top, always, whoever used it and wherever. The touch count and the kind squares say how busy it has been. A "Busiest" switch in the sort menu flips to B when you want it.

Why this one: the order is always explainable ("it's first because Moshe just added a file"), it matches how the list already reads, and the heat is still visible.

B · Busiest first

A score per job: every touch adds a point that fades over the window, so a job touched nine times this week beats one touched once an hour ago.

Trade-off: the file Moshe added a minute ago can sit in fourth place under three busier jobs — exactly the case you tested and expected on top.

C · A feed, day by day

Every touch as its own line under Today / Yesterday / This week, jobs repeating.

Trade-off: it answers "what happened" rather than "which jobs" — more reading, and a busy day is a wall.

Under the bonnet, in one paragraph

One pure function turns every source the app already has into a single list of touches — job, when, who, kind, a short sentence — and folds it per job into "last touch, touch count, kinds present". It runs once when the data changes, never per frame, so the board stays as quick as it is now. The Drive check adds two cheap things to the same call: the name of the account that changed each file, and the files trashed in the window. Nothing new is stored; the widget reads what is there. The list a number opens, the row that opens the job, the group label and the ten-minute Drive refresh all stay as they are.
