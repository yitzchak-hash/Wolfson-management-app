Problems, Tipus and Notes

The next round, drawn before it is built: a problem on an apartment and everything it touches, the tipus field, the one voice-and-text box on every input, and the notes that read like notes. Numbered red dots match the notes beside each picture; starred questions at the end are the ones only you can answer.

Nothing here is built. Say "build it" and this page is the spec.

The message box the worker's phone got today becomes the way every note and every task is written, and every recording anywhere shows its words underneath.

What holds it together

// A problem is a TASK wearing a red coat — it rides the task record, // so the thread, the photos, the worker's phone, the notebook, the // counts and the backups all come for free. No new store key. ContractorAssignment.problem?: { photosRequired: boolean; status: 'open' | 'waiting' | 'solved' | 'returned'; stageBefore: string | null; // where the apartment stood closedAt?: string; approvedAt?: string; approvedBy?: string; returnNote?: string; }; // deadline = the task's dueDate; no `days` — a problem has no day Apartment.tipus?: string; // "A2"; absent = none BoardSetting.tipusim?: string[]; // the project's list, in boardSettings // The one rule every drawing reads: problemState(apt, tasks) → 'open' | 'waiting' | null aptLabel(apt) → "47 — A2 — Aharonov" // the number, the tipus, the name
  1. aThe stage is never overwritten. A problem stores `stageBefore` and every drawing asks `problemState()` first: open → red + "!", waiting → rose, otherwise the stage as always. Approval clears the state and the apartment is simply on its stage again — nothing to restore, because nothing was moved.
  2. bThe worker's Close on a problem sets `waiting`, never `completedAt`; only the office's Approve completes the task (and the return path sets `returned` + reopens). So a problem never counts as finished until Tzvi says so, and the standing photo rule reads `problem.photosRequired` before the worker's own switch.
  3. cA problem shows on every day because the portal's day filters treat a task with `problem` as matching any day up to its deadline, and as overdue after it — the same `dayOffsets` gate, one extra branch.
  4. dTipus rides `apartments`; the list rides `boardSettings` — both already persisted, exported, imported and synced; the backup audit stays green. `aptLabel` grows one segment, so every screen that prints a number prints the tipus.
  5. eThe message box is one component (the composer lifted out of the portal). Stage notes and general notes keep their storage; only the way they are written and drawn changes, so nothing old is lost or migrated.

What I would build, in this order

  • 1. The message box as a component, and the transcript on every remaining player — everything after leans on it.
  • 2. Tipus — the field, the list in project settings, the label everywhere, bulk update, reports.
  • 3. Problems — the model and the rule, the red button and form, the three states on every drawing, the band and Approve in the window, the pending bell.
  • 4. The worker's side — red cards on every day, the deadline banner, Close → waiting, "Is this the fix for…?".
  • 5. Bulk problems and the Problems report with pictures.
  • 6. The notes tab — crossed-off stages, the open stage, bullets above the box.

Things only you can decide

★Who may approve a problem? I would make it admin users only (you and whoever you make admin) — every office user sees the band, only admins see the Approve button. Or a per-user switch "may approve problems"?
★Sending it back. If the fix is not good enough, I would give Approve a neighbour, "Send back", that takes a note and turns the card red again on his phone with your note on top. Or approve-only, and a new problem for anything left?
★The deadline's default. I would pre-fill three working days from today (Friday and Saturday skipped), editable. Or leave it blank and make it required?
★Tipus in the diagram cell. I would print "47 — A2" in the cell on the desktop and keep the phone cell to "47" with A2 under it in small type (the phone cell is 77px wide). Or the same "47 — A2" on both?
